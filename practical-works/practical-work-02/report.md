## 4. Распределение ответственности (на основе матрицы RACI)

На основе матрицы RACI, разработанной в СР1, обязанности закреплены следующим образом:

| Задача | R (Responsible) | A (Accountable) |
|--------|-----------------|-----------------|
| Создание и настройка репозитория | Руководитель (Team Lead) / Архитектор | Руководитель |
| Поддержание структуры папок и файлов | Все участники (для своих разделов) | Руководитель |
| Написание отчетов | Все участники согласно ролям | Руководитель |
| Внесение коммитов | Каждый участник за свои изменения | Руководитель |
| Проверка Pull Request (PR) | Руководитель или Архитектор | Руководитель |
| Слияние (Merge) веток | Руководитель | Руководитель |
| Резервное копирование и поддержание актуальности | Все участники | Руководитель |

## 5. Ответы на контрольные вопросы

### Что такое репозиторий и для чего он нужен?

Репозиторий — это хранилище проекта, содержащее все файлы, папки и историю их изменений. Он нужен для совместной работы, отслеживания версий, отката к предыдущим состояниям и организации структурированного хранения материалов.

### Какие преимущества даёт использование Git при командной разработке?

Git позволяет работать параллельно (через ветки), не мешая друг другу; отслеживать вклад каждого участника; безопасно сливать изменения; разрешать конфликты; иметь полную историю разработки и возможность отката.

### Что такое коммит и каким правилам должно соответствовать сообщение коммита?

Коммит — это зафиксированное состояние файлов в определенный момент времени. Сообщение должно быть кратким (до 50 символов в заголовке), информативным, описывать суть изменений (часто используется стиль Conventional Commits: `feat:`, `fix:`, `docs:` и т.д.), глаголы используются в повелительном наклонении.

### В чём разница между веткой (branch) и основной веткой (main/master)?

Основная ветка (`main`) содержит стабильный, проверенный код (часто готовый к релизу). Ветки (`branch`) создаются для изолированной разработки новых функций или исправления ошибок, чтобы не нарушать работу основного проекта до прохождения ревью.

### Что такое Pull Request и как он связан с распределением ответственности?

Pull Request (PR) — это запрос на слияние изменений из одной ветки в другую. Он связан с ответственностью, так как требует обязательного код-ревью (Reviewer — R) перед слиянием. Это гарантирует, что изменения проверены ответственным лицом (например, Team Lead — A) и соответствуют стандартам.

### Как через историю коммитов можно определить вклад каждого участника команды?

С помощью команд `git log` (с указанием автора и даты), `git shortlog -sn` (сводка по коммитам на каждого автора) и `git blame` (показывает, кто и когда изменил конкретную строку файла). Также вклад виден по количеству закрытых PR и ревью.

### Почему перед началом работы требуется регистрация на GitHub?

GitHub выступает в роли удалённого (центрального) сервера. Регистрация необходима для идентификации участников, настройки прав доступа (кто может пушить, кто только делать PR), а также для использования встроенных инструментов командной работы (Issues, Pull Requests, Projects).
